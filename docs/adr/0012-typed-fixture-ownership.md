# ADR 0012: Typed Fixture Ownership

## Status

Accepted

## Context

Scenario constants had accumulated in UI steps and product tests: accounts, error inputs, catalog
contents, sort options, checkout customers, database seed expectations, and API negative values.
This made steps invent test scenarios and duplicated product knowledge across tests.

## Decision

Bookwright uses two explicit sources of test inputs:

- stable target-owned data lives in immutable typed fixtures such as `SauceDemoFixtures`,
  `LocalUserFixtures`, and `HotelDatabaseFixtures`;
- unique or mutable scenario data is generated by the per-test deterministic `TestData` sequence.

Fixtures are injected as test parameters by the JUnit resolver. Tests select a scenario and pass its
ready values to focused steps. Steps perform actions and assertions but do not choose accounts,
products, payloads, or expected collections. Secret-bearing fixture records redact their diagnostic
representation.

A framework architecture test scans steps and product tests for known scenario literals. This is a
small, dependency-free guard against fixture data drifting back into behavior classes.

## Consequences

- Scenario ownership is visible and reusable without turning steps into data providers.
- Generated API and database values can be replayed with the recorded test seed.
- Product assertions remain explicit while their expected data has one owner.
- Adding a stable scenario requires extending the target fixture instead of embedding literals in a
  test or step.
